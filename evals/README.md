## 固定输入

每次执行使用独立目录，内含冻结的技能文件、原始附件和空输出目录。记录每个技能文件的 SHA-256。原始附件按角色命名，例如 main.pdf 与 supplement.pdf；DOCX 补充材料保留为 supplement.docx，不把改名当作格式转换。

执行快照只暴露任务所需的 `literature-*` 技能目录、`template/` 和必要依赖。`evals/`、历史候选、评分记录以及根 README 中的案例结果留在评审侧；不要把带有历史测试答案的完整仓库直接作为后续盲测输入。

验收样例只提供给评审者。执行代理不接收样例内容、预期数量、已知缺陷、其他代理输出或评审结论。修订后的测试使用新代理，不沿用旧执行上下文。主控不补写候选后再把结果归因于被测模型。

## 执行配置

记录实际请求的模型标识与推理强度。2026-11-23 的低能力压力测试使用 `gpt-5.6-luna`、`low`；这是一项历史配置，不代表对所有可选模型的能力排名。不同完整模型 ID 的结果不得仅按同一产品昵称合并。

使用不继承对话的子代理。执行代理不再创建其他代理。基线与修订版使用相同任务文字，只有输入、输出和技能快照路径不同。

任务文字模板：

```text
请使用 <技能快照>/literature-zotero2obsidian/SKILL.md 及其引用的子技能，
将 input/main.pdf（主文）和 input/supplement.pdf（补充材料）整理为完整的
Obsidian 中文文献笔记候选，附所需图件和处理记录。
本次仅生成候选，不向真实 Zotero/Obsidian 写入。
没有提供实际文献库访问；缺少库级信息时如实记录，继续完成能够根据 PDF
完成的候选内容。模板与术语表位于技能快照的 template/。
仅使用本执行目录中的源材料和技能。不要创建子代理。
请实际完成处理，不只写方案。
候选保存在 output/candidate.md，状态报告保存为 output/execution-report.md。
```

Python 代码遵循任务中的路径、进度与脚本接口要求。模型执行过程中的中断须保留原因；中断运行不作为一次完整成功或失败结果。不得隐瞒失败后挑选较好的重试。

## PDF 与 DOCX 九配置测试工具

[Hu 2024 协议](2026-11-24-hu2024-protocol.md)比较 `gpt-6-luna`、`gpt-6.1-terra`、`gpt-6.2-sol` 的 low、medium、high。协议冻结技能版本、实际输入和统一任务，不给执行者标准 Markdown。

在 Python 编辑器中打开 [model_matrix.py](model_matrix.py)，填写文件末尾 `MatrixConfig` 的六个路径和版本字段，再运行脚本。原始材料、标准 Markdown 和结果目录必须放在仓库之外。脚本从指定 Git 提交读取技能，即使工作区有未提交修改也不会混入快照。它建立九个独立目录、相同任务及评审侧清单，显示准备进度；不会调用模型，也不会把“目录准备成功”登记成测试通过。

宿主随后为每一行清单发起真实的独立模型调用，明确指定模型、推理强度及不继承历史。只告诉执行者本目录位置和读取 `task.txt`，不追加该论文的答案或修复建议。启动回执、正常结束、外部中断应分别保存。调用结束后使用 `inspect_run(run_root, manifest_path)`绑定实际候选、资源及处理记录，并核查输入、任务、技能文件是否变化。哈希检查不能证明共享宿主上的所有读取行为都已被隔离。

[inspect_markdown.py](inspect_markdown.py)的 `inspect_markdown(path, resource_root)`收集章节、行末书目锚、图片文件、Rich Table、显示公式及现有检查器发现。它只返回可复查线索，`acceptance`始终标为未评估。资源路径越出指定根目录时仅报告，不读取根外文件。候选没有图片、没有书目或检查器零错误，都不能单靠该函数得到质量通过结论。

同一候选的正文内容、资源与格式、全流程记录分别报告。只有适用的必需交付目标都有来源证据支持，才能给出文件验收通过。一次执行的通过仅适用于该输入和该次运行；确认稳定门槛还需独立复跑与更多文献。

## 独立评审

新版本比较的是同一冻结 Python 辅助层配合不同模型的交付。原始模型内容先冻结，再由同一程序统一处理；不能只为某个配置手工修补。分别保存原稿、程序变换、规范化稿、机械验收与语义评审，不把确定性格式修复归因于模型自身能力。历史输出重放是程序回归材料，不算新模型调用，也不能替代新流程的独立重复试验。

测试过程中持续按环节汇报：PDF / DOCX 提取、来源单元与阅读顺序、标题、作者单位、翻译、文字与段落拼接、引文身份识别、链接组装、图表公式及空行格式化。每个问题附候选定位、来源或执行证据、自动修复状态及仍需处理事项。发现阶段与推断起因分开；没有对应执行记录时不能把漏译直接归因为提取失败。新程序输出的 `phases.json` 和中文 `report.md` 提供实际机械环节证据。

从用户样例与原始附件建立可复用的单目标验收表。每个目标包含 ID、通过条件、来源定位、候选证据、结果和严重程度。

当前验收范围为 Markdown 文件及其引用资源，按用户参考 Markdown 的内容与格式要求比较，并用原始 PDF 核对事实。应用界面、点击跳转、插件显示和原生缓存均不安排验收。历史运行保留原冻结协议；用户变更验收范围后，在新版本中记录范围变化与新协议哈希，不回改历史分数。

| 结果 | 含义 |
|---|---|
| pass | 有证据支持该目标 |
| fail | 该目标有具体缺失或错误 |
| blocked | 验证所需的真实环境或外部数据不可用 |
| not_tested | 本次没有完成该项核验 |

下列检查分别形成目标：

- 主文内容完整性。
- 补充材料内容完整性。
- 作者与单位的对应关系。
- 公式的数学内容。
- 主文书目的逐条交付。
- SI 书目的逐条交付。
- 文内引文的对应关系。
- 每个表格的结构与原文对应关系。
- 每张工作表的锁定状态。
- 每张工作表的主题。
- 每幅图的面板完整性。
- 每幅图的图外内容排除情况。
- 原始附件的只读保护。
- 缺失环境的如实报告。

上述是检查维度索引；具体表格单元、公式、段落或图像要素仍逐项设目标。图像须打开源页和候选资源进行视觉核验，不能仅比较数量或尺寸。原文自身的差异单列，不擅自更正原文以追求表面一致。译文不要求逐字相同；新的兼容锚点按实际引用落点判定。既有 ID 保护用修复场景另验。

静态检查零错误不能替代内容验收。通过项数量不是等权质量分。只有一篇期刊论文及一份 SI 的执行不能证明其他附件格式、其他文献类型或真实库写入已经通过；测试过一份 DOCX 也不能外推到所有 DOCX。

## 规则粒度审阅

每条约束采用 `前缀-C编号`，每条验收采用 `前缀-A编号`。不同可独立失败的目标必须拆开；条件、值域和替代实现方式可以限定同一目标。拆分时对照原条目保留条件及例外。旧条目到新 ID 的映射供语义保全复核。

仓库检查器验证规则 ID、重复 ID、所属技能和复选框结构。它不根据标点或连接词推断语义原子性；语义判断需独立逐项审阅。

## 保存证据

执行清单记录模型配置、技能文件哈希、源文件哈希和候选哈希。评审保留原始候选，不覆盖模型输出。用户附件、完整笔记和生成图件不随仓库测试记录公开上传；仓库仅保存测试方法及必要汇总，完整评审作为独立交付保存。
